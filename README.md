# 好价监控

按关键词定时搜什么值得买，**只保留有新爆料的**，淘汰互动全 0 的和过期的。有互动的弹桌面通知，同时全部留档，随时能翻回去点进原文。

不做价格判断、不猜值不值——判断权在你。

---

## 规则

1. 关键词去搜，你有几个词就搜几个词
2. **每轮抓两路排序，合并去重**：最新排序（快）+ 综合排序（热）
3. 互动全 0（值、不值、收藏、评论都是 0）的直接丢
4. 门槛分两档：
   - **最新排序：值 ≥ 2 或 评论 ≥ 2**，任一条达标即可
   - **只在综合排序出现：值 ≥ 5 且 评论 ≥ 5**，两个都要够
5. 达标的推给我，我自己点进去判断

额外挡掉的三类：**已标过期/售罄的**、**发布超过 7 天的**、**只在综合排序出现且超过 48 小时的**。

门槛这样分档是有原因的：最新排序抓的是刚发的，冷门品类（机油）发布 4 小时后真的只有 2 个人点值，门槛调高会全挡掉；综合排序爬的是热帖，本来就靠人气上位，能上榜却连 5 个值 5 条评论都没有的，多半是小众配件或已过气的，不值得推。

---

## 为什么要抓两种排序

一路不够。实测同一个关键词「牛奶」、同一时刻：

| | 数量 | 说明 |
|---|---|---|
| 最新排序 | 20 条 | 都是几十分钟内的，但大多还没人投票 |
| 综合排序 | 20 条 | 都是热帖，但通常是 7–22 小时前发的 |
| **交集** | **2 条** | 几乎完全不重叠 |

只在综合排序里出现、过关门槛、且未标记过期的有 **17 条**——比如「今日必买：光明 4.0g蛋白」，值 83、评 84、藏 198。

这类东西**按最新排序永远看不到**（已经沉出前 20 了），但价格还活着。反过来，最新排序里刚发布的那批，综合排序还没收录。

所以两条都要：

```
最新排序 → 保证不漏"刚刚出现"的
综合排序 → 保证不漏"已经火了但还没死"的
   ↓ 按文章 ID 合并去重
   ↓ 同一篇两路都有的，标「最新+综合」；只在综合出现的，标「综合热门」
```

### 只挂在综合排序上的条目有时间上限

综合排序里混着已经死掉、只是还留在热榜上的老帖。实测那一批的年龄分布：

| 发布距今 | 判断 |
|---|---|
| 7–22 小时 | 有效，多是「今日必买」「国家补贴」这类长周期活动 |
| 34–45 小时 | 多数仍有效 |
| 60 / 86 / 132 小时 | **基本已死**，只是热度还在撑着 |

所以设了 `maxAgeHoursDefault: 48`——**只对「仅综合排序出现」的条目生效**，两路都有的（说明是新的）不受这条限制。

这个数字是权衡：调到 72 会多捞几条 60 小时的老帖，调到 24 会砍掉一批仍有效的次日好价。

## 数据源：搜索页 + `order=time`，纯 HTTP 采集

```
search.smzdm.com/?c=faxian&s=关键词&v=b              → 综合排序
search.smzdm.com/?c=faxian&s=关键词&order=time&v=b   → 最新排序
  → 过 WAF（只用浏览器过一次，拿 cookie）
  → 之后纯 fetch 直取完整 HTML（每页 20 条，含价格/值/评论/时间/商城）
  → 两路合并去重 → 过滤 → 推送 + 落库
```

### 为什么不用每次都开浏览器

搜索页前面是腾讯防水墙（`__TENCENT_CHAOS_VM`，95KB 混淆字节码）。它做两件事：先返 `202 + probe.js` 跑虚拟机校验，通过后下发 cookie。

**关键发现：过了这道门之后，服务端就把完整的 20 条结果直接渲染在 HTML 里**，不需要 JS 再请求接口。所以浏览器只承担"过一次门"这一个职责，剩下的 fetch 就能干。

实测对比（同一台机器、5 个关键词）：

| | 浏览器渲染 | 纯 HTTP |
|---|---|---|
| 单轮耗时 | 24–26 秒 | **10–12 秒** |
| 是否弹窗 | 每轮闪一次 Edge | **不弹** |
| 数据完整性 | 20 条 | 20 条，字段 100% 一致 |

### cookie 能活多久

实测：取一次 cookie，关掉浏览器，30 秒一次连续请求 **12 分 20 秒、25 次、跨 3 个关键词，零失效**。

注意 `w_tsfp` 这个 cookie 的 TTL 只有 118 秒，但它不是关键；真正维持放行的是长效 cookie（`__ckguid`、`device_id`）。

设计上不赌它的寿命：

```
能直接用 → 直接请求
被重新挑战（202 / probe.js）→ 自动起一次浏览器重过墙 → 重试
距上次取 cookie 超过 90 分钟 → 主动刷新一次
```

所以浏览器从"每轮必开"降级成"偶尔开一次"，多数时候一天开不了几次。cookie 缓存在 `data/waf-cookie.json`。

### 为什么不干脆用浏览器 headless

**过不了。** 风控会识别无头指纹。有头 + `--disable-blink-features=AutomationControlled` + 屏蔽 `navigator.webdriver` 才能过。这套设置写在 `src/source-http.js` 的 `harvest()` 里，只在过墙时用到。

### 为什么不用官方 API

**因为官方「好价检索 Pro」返回的不是最新好价，是一份缓慢漂移的历史榜单。**

实测（2026-11-04 下午）：

| 观察项 | 结果 |
|---|---|
| 连续 12 分钟 5 次拉取 | 4 次零变化，唯一一次变化是挤进一条 6 天前的老帖 |
| 列表里最新一条 | 停在 09:40，测试时已是 15:01，**滞后 5.5 小时** |
| 同一时刻页面 `order=time` | 第一条是 **14:45** |
| 两边 20 条列表交集 | **0 / 20，一条都不重叠** |

还有两个硬限制：

- **每个关键词最多 20 条，没有分页**（`page`/`offset`/`start` 全部无效，`size` 传 50 也只回 20）
- **没有排序参数**，参数全集只有 6 个，改不了

它的定位是"关键词相关的 top-20 商品爆料"，适合做比价参考，不适合做"发现新好价"。

### API 仍然可用

代码没删，`config.json` 里 `api.enabled` 改 `true` 就切回去。适合的场景是需要**实付价和券链接**的时候。

调用参数备忘：

| 项 | 值 |
|---|---|
| 地址 | `POST https://gw-openapi.zhidemai.com/hj-search/discount/v2` |
| 鉴权 | header `x-api-key`（**不是** `Authorization: Bearer`，写错会一直 401） |
| 必填 | `product_query` / `request_from` / `question_id` |
| 注意 | `query_process` 必须是 `1`，传 `0` 返回空 |

Key 存在 **`.env`**，不写进 `config.json`（后者会被导出、截图、发给别人）。日志里只打印 `830f***04ac` 这种脱敏形式。

## 错过了怎么办：历史页

历史页默认**只显示未读**，也就是你还没处理过的推送。处理完就清空，不会越翻越乱。

- **怎么算已读**：点标题或「去购买」打开原文自动标已读；懒得点就按右边「标记已看」，或者顶部「全部标已读」一次清干净
- **未读从什么时候开始算**：`data/reads.json` 里的 `baseline` 时刻。建这个文件之前的 71 条历史一律算已读，不会一上来就堆满
- **找东西**：顶部搜索框即时过滤标题和商城名，再配合关键词 chip、按天分组（今天 / 昨天 / 前天）
- **「全部」视图**：所有历史都在，一条都不删。**未读一律排在前面，已读沉到列表最下面**，中间有一条「已读 · N 条」分隔线
- **每条带商品图**：126px 大图，渲染时把地址里的 `_d250` 换成 `_d800`（800×800）取原图，加载失败自动退回缩略图；点图等同点标题

不删数据是有意的。老帖子哪天重新出现在搜索结果里，靠内存里的 `seen` 集合认出来才不会重复推你；删掉记录等于删掉去重依据。所以清理只发生在「你看到的列表」这一层，不发生在磁盘上。

## 改关键词

**方式一：页面上改（推荐）**

历史页顶部点「关键词」，弹窗里直接增删，保存即可。**不用重启**——采集主程序每轮开始前会重读 `config.json`，下一轮就生效。

弹窗里会自动去重（忽略大小写）、去掉首尾空格和空行，最多 40 个词。

**方式二：手改 `config.json`**

```json
{
  "keywords": [
    "5w-30机油",
    "洗衣凝珠",
    "牛奶",
    "MacBook Pro M6",
    "usmile儿童电动牙刷替换刷头"
  ]
}
```

同样不用重启，下一轮自动生效。注意上一行末尾补逗号，最后一行不加；必须是英文引号。

双十一加一批，过完删掉就行。

## 配置说明

| 字段 | 默认 | 说明 |
|---|---|---|
| `intervalMinutes` | 15 | 每轮间隔。大促可以调 10，平常 30 |
| `source` | `http` | `http`=纯请求（推荐）/ `browser`=每轮开浏览器 / `api`=官方接口 |
| `sorts` | `["time","default"]` | 抓哪几路排序。只留 `["time"]` 就是原来的单路模式 |
| `maxAgeHoursDefault` | 48 | **只在综合排序出现**的条目，超过这么多小时丢弃。两路都有的不受限 |
| `waf.maxAgeMinutes` | 90 | cookie 超过这么久主动重过一次墙。失效时也会自动重过，不用管 |
| `pages.maxPages` | 2 | 最多翻几页。**自适应**：只有第一页 20 条跨度不足一个轮询周期时才翻第二页（只对最新排序生效） |
| `skipExpired` | true | 跳过标了"过期/售罄"的 |
| `skipNoInteraction` | true | 跳过互动全 0 的 |
| `interactionGate.minWorthy` | 2 | 值达到这个数才推（默认门槛，用于最新排序） |
| `interactionGate.minComments` | 2 | 评论达到这个数才推（与「值」是或关系） |
| `interactionGate.combine` | `any` | `any` 任一达标 / `all` 全部达标 |
| `interactionGate.defaultSort.minWorthy` | 5 | **只在综合排序出现**的条目，值要达到这个数 |
| `interactionGate.defaultSort.minComments` | 5 | 同上，评论要达到这个数 |
| `interactionGate.defaultSort.combine` | `all` | `all` 表示值和评论都要够，不是或 |
| `interactionGate.defaultSort.appliesTo` | `defaultOnly` | 改 `hasDefault` 则连「两路都有」的条目也按严门槛算 |
| `maxAgeDays` | 7 | 超过几天的爆料不要。设为 0 关闭 |
| `maxItemsPerKeyword` | 40 | 每个关键词最多保留前 N 条（合并后约 25–38 条，留 40 头寸） |
| `api.enabled` | false | 改 true 走官方接口（会失去时效性，慎用） |
| `notify.maxPerRound` | 5 | 一轮超过 N 条就合并成一条汇总通知，避免刷屏 |
| `browser.executablePath` | Edge | 本机没装 Chrome，用 Edge |
| `browser.headless` | **false** | **不能改成 true**，过墙会失败 |

## 已知限制

**1. 过 WAF 时仍需真实浏览器窗口**

搜索页有腾讯防水墙，纯 HTTP 请求直接返回 `202 + probe.js`。**但只需要过一次**：过了之后 cookie 能支撑后续所有请求，实测 12 分钟连续 25 次零失效。

实际表现：

- 正常情况：**完全不弹窗**，纯 HTTP，一轮 10–12 秒
- cookie 失效时：自动起一次 Edge（窗口移到屏幕外 `--window-position=-2000,-2000`），约 3.5 秒过完墙，之后继续用 HTTP

别改 `headless: true`，无头过不了。

**2. 搜索相关性噪声**

搜 "MacBook Pro M6" 会返回笔记本内胆包；搜 "牛奶" 会返回奶片和含乳饮料。这是值得买搜索本身的问题，不是过滤逻辑。看标题能识别，你自己判断。

**3. 冷门品类一页要覆盖很久**

机油、刷头这类，20 条可能横跨几小时。好处是 15 分钟一轮绰绰有余，坏处是新爆料少的时候一页就够，翻页不会触发。

**4. 时间解析有个坑（已修）**

页面当天发布的条目只给 `11:08` 这种纯时分，**没有日期**。`store.js` 里对纯时分按"今天"算，如果晚于当前时刻则算昨天。跨零点时依赖这个判断。

**5. WAF 规则或页面结构会变**

纯 HTTP 模式依赖两个外部条件：cookie 能过墙、HTML 结构不变。

- **全 0 条 + 日志出现「WAF 挑战」**：cookie 失效了，会自动重过墙；连续失败说明规则变了
- **拿到了 HTML 但解析出 0 条**：页面结构变了，改 `src/source-http.js` 里的 `parseRows()` 正则
- **急着恢复**：把 `config.json` 的 `source` 改成 `browser`，立刻回到浏览器渲染模式，数据字段完全一样

排查工具：`node scripts/probe.js 牛奶 headful`

## 不要做的事

- 别把 `intervalMinutes` 调到 5 以下，搜索页会吃风控。
- 别开无头模式。
- 别并发搜多个关键词。代码里是串行的，每个之间停 1.5-3.5 秒，这是故意的。
- 别把 `.env` 提交到任何仓库，也别贴到聊天群里。如果泄露了，去后台重新生成一个。

## 分支说明

| 分支 | 内容 | 状态 |
|---|---|---|
| `vanilla` | 原生 JS + 手写 CSS 实现（默认分支），`src/server.js` 直接吐 HTML | 可运行 |

```bash
# 后端（两个分支都一样）
node src/server.js                 # 7788

# 只有 vue3 分支有前端工程
cd web && npm install && npm run dev   # 5173，/api 已代理到 7788
```

目录结构与 Vue 写法说明见 [`web/README.md`](web/README.md)。

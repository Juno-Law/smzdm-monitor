# 场景重定义与方案修订

> 2026-11-04 ｜ 修订 `02-竞品调研与可行性复核.md` 的结论

---

## 0. 为什么要改结论

上一版得出的结论是「80% 在重复造轮子，建议砍到只剩耗材聚合」。

那个判断建立在一个错误前提上：**假设监控对象是「一个商品链接」**。

但你给的两个场景说明，监控对象其实是**「一个需求」**：

1. 我要喝牛奶，不限品牌和规格，只要便宜
2. 链接和 SKU 会漂移，今天的关注对象明天可能就不存在

在这两个前提下，所有「绑 SKU」的工具都会失效。所以不是重复造轮子，是**现有的轮子结构不对**。

---

## 1. 问题的真正结构：三层监控对象

| 层次 | 描述 | 例子 | 稳定性 | 现有工具 |
|---|---|---|---|---|
| **L1 需求** | 我要什么，不指定品牌 | 「牛奶」「能充笔记本的充电宝」 | 极高，一年不变 | **空白** |
| **L2 规格** | 品牌 + 型号 + 容量 | 「特仑苏 250ml×12」「美孚 0W-40 5L」 | 中，同规格多链接 | 部分（关键词订阅） |
| **L3 SKU** | 某个店铺的某个链接 | `item.jd.com/100012043978.html` | **极低，随时失效** | 全覆盖 |

**关键结论：所有现成工具都工作在第 L3 层，而你的需求在 L1-L2。**

- 值得买 App 降价提醒 → 绑 L3，链接一换就失效
- 慢慢买关键词订阅 → 能到 L2，但只推送不判定，噪声大
- GitHub `zdm` 项目 → 抓 L1 的爆料流，但只有白名单标题匹配，没有规格和价格逻辑

这是结构性的空白，不是功能缺失。

## 2. 场景 A：不限品牌规格，只要有货就对

### 2.1 先拆穿一个伪需求

你说「都可以」，但实际上你不会买：

- 9.9 元 12 盒的杂牌「含乳饮料」（不是牛奶）
- 临期清仓的进口奶（还有 5 天保质期）
- 200ml 小样装（单价并不便宜）
- 奶粉、酸奶、奶片（搜「牛奶」全都会命中）

所以真实需求不是「都可以」，而是：**「在合理的品牌和规格范围内，单价足够低」**。

「都可以」翻译成可执行条件时，必须补齐三类隐性约束：

| 约束类型 | 牛奶场景 | 作用 |
|---|---|---|
| **品类硬约束** | 必须含「牛奶/纯牛奶」，排除「乳饮料/含乳饮品/奶粉/酸奶/奶片」 | 防止品类漂移 |
| **规格硬约束** | 排除「临期/清仓/小样/试用/赠品」，单件容量 ≥ 200ml | 防止低价陷阱 |
| **价值判断** | 元/L ≤ 阈值，值率 ≥ 80% | 判断是不是真好价 |

这就是产品经理要做的翻译工作：用户说「随便」，意思是「你帮我判断」，不是「什么都行」。

### 2.2 品类模板（核心资产）

每个品类一套判定逻辑，这是系统真正的价值所在，也是别人抄不走的个人配置。

| 品类 | 归一化单位 | 参考好价线 | 必排词 | 预期频次 |
|---|---|---|---|---|
| 常温纯牛奶 | 元/L | ≤ 10 | 临期、清仓、乳饮料、奶粉、酸奶、小样 | 每周 3-5 条 |
| 鲜牛奶 | 元/L | ≤ 15 | 同上 + 常温 | 每周 1-2 条 |
| 全合成机油 | 元/L | ≤ 56（0W-40） | 二手、翻新、1L、柴机油、摩托车 | 每月 1-2 条 |
| 抽纸 | 元/包(100抽) | ≤ 1.5 | 手帕纸、湿巾、卷纸 | 每周 2-4 条 |
| 充电宝 | 元/10000mAh | ≤ 60 | 电芯、电池、保护壳、数据线 | 每月 2-3 条 |
| 笔记本 | 台（按型号） | 人工设 | 二手、官换、配件、贴膜 | 每月 0-1 条 |

「预期频次」这一列很重要：**机油一个月没消息是正常的，牛奶一周没消息说明系统坏了**。看板要按品类显示「距上次命中 N 天」，避免你以为它还在工作。

### 2.3 规格解析是核心工程

标题长这样，要从里面算出总容量：

```
蒙牛 特仑苏 纯牛奶 250ml*12盒        → 3.0 L
伊利 金典 有机纯牛奶 250ml*16盒       → 4.0 L
光明 优倍 鲜牛奶 950ml               → 0.95 L
德运 全脂牛奶 1L*10                  → 10 L
```

解析规则：正则提取「数字 + 单位（ml/L/g/kg/片/包/抽）」+ 乘数（`*12`、`×12`、`12盒`），统一折算。

**必须设计失败路径**，因为一定会有解析不出来的：

```
解析成功 → 参与单价比较
解析失败 → 标记 spec_unknown
         → 不参与单价比较，只按「官方标签 + 值率」判定
         → 看板标注「规格待确认」，可手动补
```

宁可漏掉一条，也不能把 1L 装的价当成 5L 装的价推给你——错一次，这个系统你就再也不信了。

## 3. 场景 B：链接和 SKU 会漂移

### 3.1 问题本质

你把「关注」绑在一个会消失的实体上。而 L3 层的东西平均寿命很短：商品下架重上、换店铺、换包装、换货号、活动结束链接失效。

更糟的是：**App 不会告诉你提醒已经死了**。你以为在监控，其实三个月前就失效了。

### 3.2 三层解法

**① 主链路改成事件流，从根上免疫**

不要轮询商品页，而是消费「爆料流」。

爆料是**事件**：每条爆料诞生时自带新链接、新 SKU、新价格。链接失效不影响新事件产生。只要有人爆了「牛奶好价」，它就一定会出现在流里，与你之前关注过什么无关。

这一条直接消灭了「链接失效」这个类别的问题，还顺带省掉了反爬、cookie、selenium 这些维护地狱。

**② 商品身份归一（canonical id）**

需要盯具体型号时，用「品牌 + 型号 + 规格」生成稳定 ID，多链接映射到同一个 ID：

```
canonical_key = hash(normalize(brand) + normalize(model) + normalize(spec))

蒙牛 特仑苏 250ml*12  →  key_a
京东链接1  →  key_a
天猫链接2  →  key_a
拼多多链接3 →  key_a
```

换链接，`key_a` 不变，历史价格、判定规则、命中记录都不断。

**③ 失效巡检**

对已绑定的 L3 链接定期探活：404 / 下架 / 价格消失 → 标记 `DEAD`，并尝试在爆料流里按同一 `canonical_key` 找新链接自动补位；找不到就在看板标红「该关注项已失效，建议重绑」。

**这是「你会不会发现它坏了」的问题**，比修复本身更重要。

## 4. 重新定位

| 旧定位 | 新定位 |
|---|---|
| 价格监控器：盯住商品，降价就通知 | **好价过滤器：输入需求，输出值得买的爆料** |
| 核心是采集和反爬 | 核心是**匹配 + 规格解析 + 单价归一 + 判定** |
| 会被链接失效拖死 | 事件流，天然免疫 |
| 和 App 功能重叠 | 覆盖 App 架构上做不到的 L1-L2 层 |

一句话：**你要的不是「降价提醒」，是「好价筛子」。**

---

## 5. 修订后的路线

### MVP-0：先验证「爆料流里有货」（一天）

最大的不确定性不是判定准不准，而是**有没有人爆牛奶的料**。如果一周只有两条，做多精准的引擎都没用。

做法：关键词过滤 + 每日一封汇总（或一条 Toast），列出昨天命中的爆料，按值率排序，不做任何价格判定。

观察一周：
- 每天几条？品牌和规格分布如何？
- 有没有你看到就想点进去的？
- 如果 0-1 条/天 → 这个品类不值得做监控，关掉

**先验证供给，再投资判定。**

### MVP-1：加判定层（fork `zdm` 的采集和推送）

复用它的：爆料流拉取、SQLite 去重、邮件/微信推送、GitHub Actions 定时。
重写它的：标题匹配 → 规格解析 → 单价归一 → 规则判定。
新增：桌面 Toast、品类模板配置。

### MVP-2：看板与复盘

- 按品类显示命中数、距上次命中天数
- 每条命中标注「命中哪条规则」
- 「买了 / 不感兴趣」反馈，不感兴趣自动进排除词
- 失效关注项标红

## 6. 待验证的假设

| 假设 | 验证方式 | 如果不成立 |
|---|---|---|
| 爆料流里牛奶类供给足够（≥2条/天） | MVP-0 跑一周 | 该品类不做，只保留机油/数码 |
| 标题里能稳定解析出规格（≥80%） | 抽 50 条人工标注 | 降级为只按标签+值率判定 |
| 「好价线」可以事先定出来 | 用历史爆料反推分位 | 改为「低于近 90 天均价」动态判定 |
| 你不介意每天扫一眼汇总 | 用一周 | 改成只在命中时推送 |

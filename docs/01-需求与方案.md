# 好价监控系统 · 需求与方案

> 版本 v0.1 ｜ 2026-11-04 ｜ 形态：本地常驻服务 + 网页看板

---

## 0. 一页纸

**要解决的问题**：把「我主动去什么值得买上蹲」变成「符合我标准的好价主动来找我」。

**核心判断**：不自己爬京东/淘宝的价格，而是消费值得买上**已经被真人验证过的好价流**，用本地关注清单做匹配。
理由：到手价（券后、满减、会员价、需买N件）自己算不准；电商反爬成本高；而值得买官方接口直接给了 `digital_price`（实付价）、`coupon`（券链接）、`zhifa_tag`（神价格/绝对值/历史低价）、`article_worthy`（值率）、`article_is_sold_out`（售罄状态）。

**北极星指标**：推送命中率 = 点击购买链接的推送数 / 总推送数。
这个指标决定了产品生死——命中率低，三天就会被关掉。所有设计（去重、冷却、静默时段）都是为它服务。

**非目标**（明确不做，防止范围蔓延）：
- 自动下单、自动领券代抢（账号风险、法律灰区）
- 全平台比价（京东/淘宝/拼多多实时比价）
- 价格预测、AI 议价建议
- 多人协作、分享清单

## 1. 需求定义

### 1.1 用户故事

| 编号 | 故事 | 验收 |
|---|---|---|
| US-01 | 我把想买的东西加进清单，不用记 | 支持从值得买商品页/搜索结果一键加入；支持手填关键词 |
| US-02 | 出现符合我标准的好价时，电脑上弹通知 | 通知含商品名、实付价、商城、命中理由；点击打开看板详情 |
| US-03 | 我能给不同商品设不同标准 | 每个清单项可独立配置规则；未配置时继承全局模板 |
| US-04 | 我不想被重复消息轰炸 | 同一爆料只推一次；同一清单项 24h 内最多一次；一批合并成一条 |
| US-05 | 我想回看这个月错过了什么、买了什么 | 看板按时间列出所有命中，标注已点击/已购买/已忽略 |
| US-06 | 耗材要按单价比较，不是按总价 | 机油按元/L、抽纸按元/包归一化后判定 |

### 1.2 三类监控对象（关键抽象）

很多人做这类工具失败，是因为把「监控对象」当成一个东西。实际上有三种，匹配逻辑完全不同：

| 类型 | 例子 | 匹配方式 | 判定重点 |
|---|---|---|---|
| **型号型** | 笔记本 `ThinkBook 14+ 2024 R7`、充电宝 `酷态科 CP6` | 型号精确匹配 + 别名表 | 是否官方渠道、是否翻新 |
| **耗材型** | 机油 `美孚1号 0W-40`、抽纸、洗衣液 | 品牌 + 规格词全部命中 | **单位价格**（元/L、元/包） |
| **品类型** | 「65W 氮化镓充电器」「27寸 4K 显示器」 | 宽泛关键词 + 排除词 | 值率、品牌白名单 |

## 2. 核心设计一：关注清单与匹配

### 2.1 清单项模型

一个清单项不是「一个关键词」，而是一组结构化条件：

```
{
  "name": "美孚1号 0W-40 全合成",
  "type": "CONSUMABLE",
  "required_terms": ["美孚", "0W-40", "5L"],   // 必须全部出现
  "any_terms": [],                              // 出现任一即可（与 required 二选一）
  "exclude_terms": ["二手", "翻新", "1L", "4L", "柴机油"],
  "alias": {
    "美孚": ["Mobil", "美孚1号", "金美孚"],
    "0W-40": ["0W40", "0W-40", "0w40"]
  },
  "unit_norm": { "amount": 5, "unit": "L" },    // 用于算元/L
  "priority": "HIGH",
  "enabled": true
}
```

**为什么要 required + exclude 而不是一个关键词**：
实测爆料标题长这样——`美孚（Mobil）1号 全合成机油 0W-40 SN级 5L 汽车保养 含机滤`。
单关键词「美孚」会命中 1L 装、柴机油、机滤套装；只有「品牌 + 规格 + 排除词」三者组合，才能压住误报。

**归一化规则**（否则匹配会漏）：
- 全角转半角、大小写统一、去空格
- `0W-40` / `0W40` / `0w-40` 视为同一
- 中文数字与阿拉伯数字（`5升` / `5L`）
- 标题中「需买2件」「PLUS会员」等营销词在匹配前剥离

### 2.2 匹配流程

```
拉取一批好价 (article[])
  → 对每条，遍历启用的清单项
  → 归一化标题 = normalize(article_title + " " + article_content)
  → required_terms 全部命中？ any_terms 至少一个命中？ exclude_terms 一个都不命中？
  → 命中则进入判定阶段
```

**性能**：清单项 < 200 时，纯内存遍历完全够用（一批 200 条爆料 × 200 清单项 = 4 万次字符串匹配，毫秒级）。不需要上搜索引擎。

## 3. 核心设计二：判定规则引擎（可自定义）

你问的「能不能自定义」，答案是可以，而且它必须是可组合的，不能只是一个价格上限。

### 3.1 规则模型

```
Rule = {
  logic: "AND" | "OR",
  conditions: [ Condition, ... ]
}

Condition = {
  type: PRICE_BELOW | UNIT_PRICE_BELOW | DISCOUNT_OFF | TAG_IN
      | WORTHY_RATE | MALL_IN | BRAND_IN | TITLE_MATCH | COMMENT_MIN,
  params: { ... },
  negate: false
}
```

### 3.2 可用条件

| 条件类型 | 参数 | 说明 |
|---|---|---|
| `PRICE_BELOW` | `amount: 280` | 实付价 ≤ 280（用 `digital_price`，不是页面价） |
| `UNIT_PRICE_BELOW` | `amount: 56, unit: "L"` | 元/L ≤ 56，耗材专用 |
| `DISCOUNT_OFF` | `ratio: 0.15, window: 90` | 低于近 90 天均价 15% 以上 |
| `TAG_IN` | `tags: ["绝对值","神价格","历史低价"]` | 命中值得买官方值法标签 |
| `WORTHY_RATE` | `min_rate: 0.85, min_votes: 20` | 值率 ≥ 85% 且投票数 ≥ 20 |
| `MALL_IN` | `malls: ["京东","天猫"]` | 限定商城，排除第三方小店 |
| `BRAND_IN` | `brands: ["Anker","酷态科"]` | 品牌白名单 |
| `TITLE_MATCH` | `regex: "..."` | 正则兜底 |
| `COMMENT_MIN` | `n: 30` | 评论数下限，过滤冷门爆料 |

每个条件都支持 `negate: true`，例如「商城不是拼多多」。

### 3.3 四个预置模板

| 模板 | 规则 | 适用 |
|---|---|---|
| **抄底型** | `TAG_IN([绝对值,神价格]) AND WORTHY_RATE(85%,20)` | 笔记本、耳机等大件，不设心理价，只等官方认证的底价 |
| **目标价型** | `PRICE_BELOW(X)` | 你明确知道该出多少钱的东西 |
| **耗材型** | `UNIT_PRICE_BELOW(Y) AND (TAG_IN OR WORTHY_RATE(80%,10))` | 机油、纸品、洗衣液、猫粮 |
| **尝鲜型** | `PRICE_BELOW(X) AND MALL_IN([京东,天猫]) AND NOT TITLE_MATCH(二手|翻新|官换)` | 品类型监控，防止买到问题货 |

**冷启动问题要诚实说**：`DISCOUNT_OFF` 依赖历史价格，系统刚上线时没有数据。所以第一版不启用这个条件，等 `price_history` 攒够 90 天再开。在此之前用「目标价 + 官方标签」兜底。

### 3.4 判定核心代码（示意）

```java
public boolean evaluate(RuleNode node, DealContext ctx) {
    if (node.isLeaf()) {
        boolean r = node.condition.matches(ctx);
        return node.condition.negate ? !r : r;
    }
    return node.logic == AND
        ? node.children.stream().allMatch(c -> evaluate(c, ctx))
        : node.children.stream().anyMatch(c -> evaluate(c, ctx));
}
```

规则以 JSON 存在 SQLite 的 TEXT 字段，Jackson 反序列化。做条件增删的 UI 时，前端只是编辑这棵树，不需要后端改动。

## 4. 核心设计三：去重与推送节奏

这是最容易被忽视、却最影响体验的部分。

**三层去重**：
1. `article_id` 级：同一条爆料永久只处理一次（Redis 式内存 Set + 落库）
2. 清单项级：同一清单项 24 小时内最多推 1 次（除非新价格比上次再低 5% 以上，视为「更低了」二次提醒）
3. 批次级：一次调度产生的多条命中，合并成 1 条通知，正文列出前 3 条

**静默时段**：23:00–08:00 只入库不推送，次日 08:30 汇总推送一条「夜间好价 X 条」。

**推送内容设计**（决定点击率）：

```
【美孚1号 0W-40】¥268（合 53.6 元/L）
京东自营 · 值率 94% · 绝对值
比你的目标价低 12 元
→ 点击查看
```

必须包含：**命中了哪条规则**。用户要知道「为什么推给我」，否则第二次就不信了。

## 5. 数据源

### 5.1 主链路：值得买好价接口

官方开放平台（`openapi.zhidemai.com` / 海纳 `ai.zhidemai.com`），手机号注册后可申请测试 Key，需审核。

关键返回字段映射：

| 接口字段 | 用途 |
|---|---|
| `article_title` / `article_subtitle` | 匹配与展示 |
| `page_price` | 页面价，用于展示「原价」对比 |
| `digital_price` | **实付折后价，判定主依据** |
| `coin_unit` | 价格单位（元） |
| `clean_link` | 干净商品链接，推送跳转目标 |
| `article_mall` | 商城，用于 `MALL_IN` |
| `coupon[]` | 券信息 + 领券链接 |
| `zhifa_tag[]` | 值法标签：神价格/绝对值/历史低价 |
| `article_worthy` / `article_unworthy` | 值率计算 |
| `article_is_sold_out` / `article_is_timeout` | 售罄/过期，直接跳过 |
| `article_pubdate` | 用于增量拉取（翻页游标） |
| `article_type` | 精选/发现 |
| `brand` / `article_top_category` | 分类过滤 |

请求参数支持 `category`、`brand`、`malls`、`channel_ids`、`start_time`、`pubdate`（游标）。

### 5.2 兜底链路：页面解析

接口不可用（未过审、超配额、字段缺失）时降级：
- 抓 `https://www.smzdm.com/p/{id}/` 取标题、页面价、标签
- 抓不到实付价时，**不猜**，标记 `price_confidence: LOW`，规则里含 `UNIT_PRICE_BELOW` 的条目跳过并记录日志

**原则：宁可不推，也不推错的价。** 一条错价推送造成的信任损失，需要十条对的才能补回来。

### 5.3 频率

- 好价流：每 20 分钟一次，随机抖动 ±5 分钟（固定间隔容易被识别）
- 单品兜底轮询：每 6 小时一次，仅针对「7 天内无任何爆料」的清单项
- 请求头带正常 UA / Referer，单次请求间隔 2–5 秒

## 6. 技术架构

### 6.1 选型

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **JDK 21 + Spring Boot 3.3** | 你最熟，改规则、加逻辑成本最低 |
| 调度 | Spring `@Scheduled` + ShedLock（单机可省） | 无额外中间件 |
| 存储 | **SQLite**（sqlite-jdbc） | 单文件，免安装，随时用 DB 工具打开看数据 |
| 前端 | 原生 HTML + Alpine.js + ECharts | 不做构建流程，改完刷新即生效 |
| 通知 | **Windows 原生 Toast**（已验证可用） | 零依赖，Java 通过 ProcessBuilder 调 PowerShell |
| 打包 | `mvn package` 出 jar + 启动脚本 | 双击 `start.bat` 即跑 |

**JDK 问题**：本机是 1.8，Spring Boot 3 需要 17+。两个选择：
- **推荐**：装 JDK 21（Temurin），`JAVA_HOME` 指过去。JDK 8 已经太老，顺手解决。
- 备选：不装 JDK，改用 Node 22 + 内置 `node:sqlite`，当天能跑通，但后续你维护起来不如 Java 顺手。

### 6.3 数据模型

```sql
-- 清单项
CREATE TABLE watch_item (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  type TEXT NOT NULL,              -- MODEL / CONSUMABLE / CATEGORY
  required_terms TEXT,             -- JSON array
  any_terms TEXT,
  exclude_terms TEXT,
  alias TEXT,                      -- JSON map
  unit_amount REAL, unit_name TEXT,
  priority TEXT DEFAULT 'NORMAL',
  rule_id INTEGER,                 -- 为空则继承全局模板
  enabled INTEGER DEFAULT 1,
  created_at TEXT, last_hit_at TEXT
);

-- 规则
CREATE TABLE rule (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  logic TEXT NOT NULL,             -- AND / OR
  conditions TEXT NOT NULL,        -- JSON 条件数组
  is_global_default INTEGER DEFAULT 0
);

-- 好价原始数据
CREATE TABLE deal (
  article_id TEXT PRIMARY KEY,
  title TEXT, subtitle TEXT,
  page_price REAL, digital_price REAL, price_confidence TEXT,
  mall TEXT, brand TEXT, category TEXT,
  clean_link TEXT, article_url TEXT,
  tags TEXT,                       -- JSON
  worthy INTEGER, unworthy INTEGER,
  sold_out INTEGER, expired INTEGER,
  pubdate TEXT, fetched_at TEXT
);

-- 价格历史（供 DISCOUNT_OFF 与曲线用）
CREATE TABLE price_history (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  watch_item_id INTEGER, article_id TEXT,
  price REAL, unit_price REAL, recorded_at TEXT
);

-- 推送记录（去重 + 命中率统计）
CREATE TABLE push_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  deal_article_id TEXT, watch_item_id INTEGER,
  matched_rule TEXT,               -- 命中的条件描述
  pushed_at TEXT,
  clicked_at TEXT,                 -- 看板跳转时回写
  feedback TEXT                    -- BOUGHT / IGNORED / NULL
);
```

### 6.4 调度主流程

```
每 20 分钟：
  1. 拉取好价流增量（游标 = 上批最大 pubdate），失败则降级页面解析
  2. 入库 deal，过滤 sold_out / expired
  3. 遍历 watch_item 匹配
  4. 对命中的，按 rule_id → 全局默认规则 判定
  5. 去重三重过滤
  6. 生成通知（合并批次），静默时段则入队
  7. 写 push_log
```

### 6.5 通知实现（已在本机验证）

Java 侧不引第三方库，直接起 PowerShell 进程：

```java
String ps = """
  [void][Windows.UI.Notifications.ToastNotificationManager, Windows.UI.Notifications, ContentType=WindowsRuntime]
  [void][Windows.Data.Xml.Dom.XmlDocument, Windows.Data.Xml.Dom, ContentType=WindowsRuntime]
  $x = New-Object Windows.Data.Xml.Dom.XmlDocument
  $x.LoadXml('<toast><visual><binding template="ToastGeneric"><text>%s</text><text>%s</text></binding></visual></toast>')
  $t = New-Object Windows.UI.Notifications.ToastNotification $x
  [Windows.UI.Notifications.ToastNotificationManager]::CreateToastNotifier('{1AC14E77-02E7-4E5D-B744-2EB1AE5198B7}\\WindowsPowerShell\\v1.0\\powershell.exe').Show($t)
  """.formatted(escape(title), escape(body));

new ProcessBuilder("powershell", "-NoProfile", "-Command", ps).start();
```

注意：XML 内容必须转义 `& < > "`，否则标题里带 `&` 就整条通知失败。

**Toast 的局限**：点击只能唤起一个 AppID，不能直接跳 URL。所以点击后打开本地看板，详情页再给「去购买」按钮——这反而更好，因为看板能记录点击行为，正好是北极星指标的数据来源。

## 7. 里程碑

| 阶段 | 目标 | 交付 | 验证方式 |
|---|---|---|---|
| **M0 通链** | 证明数据拿得到、通知弹得出 | 一个 main 方法：拉一次好价 → 打印命中 → 弹 Toast | 手工跑，看终端输出 |
| **M1 可用** | 每天真的用得起来 | 清单 CRUD 页 + 调度 + 规则引擎 + Toast + 命中列表 | 连续跑 3 天，统计命中率 |
| **M2 好用** | 降低误报、看清趋势 | 单价归一、静默汇总、价格曲线、反馈按钮（买了/不感兴趣） | 命中率应 > 30% |
| **M3 可选** | 7×24 与多端 | 搬云服务器、微信推送 | 看你是否需要离开电脑 |

**建议先做 M0，别直接写完整系统。** 通链阶段最大的风险是接口审核不过或字段和文档不符，这件事必须在写业务代码之前确认。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 开放平台审核不通过 | 主链路断 | 先做页面解析降级；M0 同时验证两条链路 |
| 接口配额不足 | 拉取频率受限 | 20 分钟一次约 72 次/天，一般够；不够则只拉关注品牌/分类，缩小范围 |
| 好价覆盖不足（冷门型号没人爆料） | 漏价 | 单品兜底轮询；对这类清单项降低预期，告诉用户「靠爆料，不保证时效」 |
| 标题匹配误报（1L 装当成 5L） | 推荐错误 | required + exclude 双保险；误报可一键「不感兴趣」并自动加入 exclude_terms |
| 推送疲劳 | 关掉通知 | 冷却 + 合并 + 静默 + 只推高优先级；命中率低于 20% 时自动降频 |
| 规则配太严，一条都不推 | 以为系统坏了 | 看板显示「近 7 天扫描 N 条，命中 0 条」，并提示建议放宽哪条条件 |

## 9. 验收标准（M1）

- [ ] 添加 5 个清单项，覆盖型号/耗材/品类三种类型
- [ ] 连续运行 3 天，每天至少完成 60 次调度
- [ ] 弹出的通知里，实付价与爆料页一致（抽检 10 条，错误 ≤ 1）
- [ ] 同一条爆料不重复推送
- [ ] 通知正文能说清「命中了哪条规则」
- [ ] 看板能按时间回看所有命中，并记录点击
- [ ] 关机重启后自动恢复调度
